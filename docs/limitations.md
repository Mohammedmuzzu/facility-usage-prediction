# Limits and external release requirements

The architecture audit resolves engineering defects within the documented single-community service contract. It cannot prove every possible scenario or replace absent business evidence. No cloud deployment or real notification delivery has occurred.

- **E01: real data and availability.** All 12,500 original observations are synthetic. Actual booking-system integration, capacity/availability, session duration, eligibility, cancellations and attendance/no-shows need provider schemas and labelled data. Resident references are scoped to the synthetic R-0001–R-9999 namespace. Real providers need a reviewed identifier mapping and privacy/retention/access controls. The CSV adapter is append-only, not an invented vendor connector.
- **E02: notification effectiveness.** Actual booking creation is only a readiness proxy. Delivery/seen/clicked/conversion labels and controlled experiments are missing. There is no optimal-notification claim, validated causal benefit or notification sender.
- **E03: organization deployment.** TLS/SSO gateway, secret-manager provisioning, multi-host quotas, slow-client/read deadlines, monitoring storage/alerts, retention, SLOs and recovery objectives need organizational deployment decisions. The supplied container and service hooks are tested; those external systems are not provisioned. SQLite quotas coordinate one host/shared volume; counters are per process. The dashboard must remain behind a private authenticated proxy, including its media endpoints.
- **E04: task and business validity.** The task assumes another booking exists and does not estimate booking probability or churn. Cutoffs are trained at prior booking creation; arbitrary later cutoffs carry warnings and lack prospective policy validation. The original holdout is a reused regression benchmark. Independent seed confirmation and three development windows add synthetic evidence, not real-resident validation. Cold-start cohort support is tiny and explicitly counted.

Timing remains uncertain, rare classes remain difficult, and a validation-selected route does not guarantee the best result on every final-test metric. Independent components propagate usage uncertainty into the notification proxy. Empirical p90 guides and resident bootstrap intervals are not calibrated prediction guarantees. Quarter-transition support is absent in the original final holdout, though development backtests report supported transitions. Feature PSI is an investigation heuristic; cumulative activity naturally drifts.

Trusted Joblib artifacts can execute code. Hash manifests detect corruption but do not authenticate an adversary-replaced manifest. Restrict release writes and trust reviewed image/release digests. Loaders enforce exact key runtime dependency versions and feature/source compatibility. Release activation is atomic, while workers pin a release until restarted. Rollback may require the matching source/runtime image and history snapshot.

Synthetic historical data is stale for live service use. Production /ready returns 503 until a recent valid append-only snapshot is supplied. Model/data contract failures, invalid keys/scopes and overload fail closed. Development mode is intentionally local and must not be exposed publicly. Docker/Compose resource values are starting bounds, not an approved capacity SLA or evidence of enterprise-scale throughput.

Future work depends on E01–E04: prospective real-data evaluation, event-provider integration, availability-aware candidate filtering, occurrence/conversion models, calibrated uncertainty, cross-community cohorts, drift-triggered reviewed retraining and experimental reminder-policy optimization. The production business-approval gate remains false until the required evidence and owner thresholds are supplied.
