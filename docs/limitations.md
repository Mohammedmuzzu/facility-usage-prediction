# Limitations and next steps

- **Synthetic data:** hand-specified behaviours create a controlled benchmark. No real-world accuracy or resident preference is established. The generator is neither learned from actual logs nor capacity-constrained.
- **Conditional prediction:** next observed booking is assumed to exist. Inactivity and probability of any booking are not estimated. Finite observation windows exclude residents' unobserved future events.
- **Reminder proxy:** actual booking creation is used as an observable readiness proxy. There are no notification delivery, engagement or conversion labels and no experimentally validated optimal send time. This application sends no notifications.
- **Timing uncertainty:** days, hours and lead are independently modelled, so errors propagate. Circular means may fall between multiple preferred times. Model scores are uncalibrated; there are no validated probability or prediction-interval guarantees.
- **History and drift:** cold starts rely on global medians, sparse users have noisy preferences, and abrupt behaviour changes are not observed in advance. The preference-shift slice is a history-only diagnostic, not ground-truth drift detection.
- **Chronology:** one global development/test split is verified. Results do not prove robustness across years, communities or new seasonal conditions. The retained final holdout has no calendar-quarter transition events, so seasonal-transition error comparisons are unavailable. Crossing-cutoff purging changes retained partition sizes; exact counts and boundaries are recorded. Infrequent histories are disproportionately excluded near boundaries.
- **Decision time:** training cutoffs occur at booking creation. Daily or arbitrary later-cutoff policies would need separate sampling and validation. Retrospective cutoffs earlier than model readiness require another historical fit.
- **Business rules:** availability, facility capacity, duration, overlapping sessions, eligibility, costs, cancellations and no-shows are absent. Usage means scheduled usage, not attendance.
- **Privacy and deployment:** references are synthetic. Real-data ingestion would need consent/access control, retention rules, minimization and pseudonymization. The local API/dashboard do not implement production authentication, persistence or multi-tenant authorization. Only load trusted Joblib artifacts.
- **Reproducibility:** seed, environment and dataset hashes are fixed; identical numeric results are verified locally. Architecture/library differences may alter floating-point details; Excel cannot store nanosecond precision, so full evaluated values remain in CSV/JSON.

Next steps: integrate real booking-system events and availability; add conversion and booking-probability labels; track delivered/seen/clicked notifications and experiments; evaluate additional chronological windows and community cohorts; calibrate uncertainty; compare Markov/CatBoost alternatives on development data; monitor feature/label drift; define an explicit retraining policy; and A/B test reminder policies before any effectiveness claim.
